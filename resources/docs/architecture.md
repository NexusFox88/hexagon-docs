# Implementation design

Status: local implementation has scoped compatibility evidence. The expanded MiniMax Sandbox × Harness × protocol matrix is tracked separately; catalog availability is not a verification claim. Daytona is a future candidate, excluded from the public catalog by user direction on 2026-11-16. `testing/acceptance.md` and `testing/execution-matrix.md` are the acceptance authority.

The user journey in testing/acceptance.md is the delivery contract. A local TypeScript control plane and PostgreSQL coordinate cloud sandboxes. A sandbox-local runtime hosts interchangeable harnesses and calls the user's model endpoint through scoped credential access. Console handles provider CRUD, credential onboarding and Fleet views. Python and TypeScript clients share HTTP/event semantics.

## Ownership
apps/control-plane assembles HTTP routes, persistence and workers. modules/execution owns sessions, runs, approvals and persisted events. modules/sandboxes owns configured connections, cloud resource IDs and cleanup operations. modules/tool-connections owns authorization state. modules/credentials owns encrypted secret references. integrations/sandboxes translates cloud APIs. runtime owns process supervision and harness interaction. Console consumes the same API as clients.

PostgreSQL transactions atomically change state and append events. Run submission uses tenant/session-scoped idempotency keys. One writable Run per Session; workers use leases and fencing. Remote create/delete operations persist intent and track uncertain outcomes. Secret encryption uses a local key outside the database. Artifacts survive sandbox cleanup in control-plane storage. Preview access requires current authorization and expiry checks.

Disabling a Sandbox or model connection blocks new Sessions and new Runs on existing Sessions. Run submission locks and checks both connections; a retry of an already accepted idempotency key still returns its original Run. The worker checks again before creating a new Harness invocation, covering disablement after queueing. An already persisted invocation remains recoverable, and resource cleanup still uses the stored connection credentials while disabled. Configuration/credential changes invalidate validation and disable the connection until revalidated and explicitly enabled. Existing Sessions keep their pinned configuration. Deleting a connection requires all dependent Sessions to be closed and does not revoke the provider credential or delete the provider account.

## Implementation order
1. Persistent domain model, auth scope, secret store and API skeleton.
2. Provider adapters and sandbox runtime with deterministic process fixture.
3. Actual model-driven harness, external tool authorization and approval continuation.
4. Console and both SDKs over the same API.
5. Entire user journey, alternate combinations, fault cases and verified cloud cleanup.

No LLM gateway or memory product. Console observes conversations and execution; applications submit messages through the API/SDK. The API Playground is a developer debugging client of the same API and can submit a real request. No commits. Do not replace actual harness execution with a canned result. Runtime engines/providers are selected after checking available credentials and API capabilities; capability gaps must be reported, not hidden.

## Harness integration boundary

`modules/execution/harness.ts` defines the executable adapter and version registry. Composition registers adapters once, derives the advertised catalog from that registry, and injects the registry into the worker. The worker resolves the exact Session-pinned id/version for installation, invocation construction and final output interpretation. Unknown versions have no fallback. Native session identifiers remain adapter-owned values persisted by the worker for later Runs.

OpenCode 1.2.27 and Pi 1.5.2 are registered implementations. Pi uses the sandbox’s native Node when it satisfies the minimum version, otherwise installs the fixed fallback Node runtime, and installs an extension that registers the user's Anthropic-compatible endpoint and forwards tools through the same Run-scoped mailbox. Authorization, approval, durable events and artifacts remain shared control-plane behavior. Tenant-owned custom source packages use `HarnessPackages` and the same registry. They are persisted as immutable id/version/content-digest records; registration never executes source in the control plane. The package adapter installs and verifies bytes via SandboxConnector and invokes an explicit interpreter inside the Sandbox. Public API and SDK registration, the stdin/result protocol and limits are described in docs/custom-harnesses.md. Cloud provider operations remain in SandboxConnector, so adding a Harness does not require provider-specific branches in execution orchestration.

## Interrupted Runtime recovery

Initial provisioning distinguishes `reserved` / `preparing` from `starting`. Directory creation and Runtime file uploads happen in `preparing`, before any process launch; a worker can repeat this preparation after interruption. Directory command exit status is checked before uploading. The worker persists `starting` only after preparation and a lease check, immediately before launching the supervisor. A recovered `starting` binding is health-checked, never automatically relaunched. Thus a lost launch response (including the intent-before-launch crash window) remains uncertain, while partial file preparation can recover. Already initialized Runtime bindings continue to use the existing no-restart rules below.

Recovery events and Run errors include a fixed execution stage and sanitized error category, numeric HTTP status and allowlisted transport code when available. Sandbox create operations retain the same sanitized failure diagnostic. Messages, URLs, provider response bodies and arbitrary error codes are excluded. These diagnostics do not turn an unknown remote outcome into permission to retry creation.

A supervisor restart quarantines previously active invocations. Persisted Tool mailboxes are retained but offered for dispatch only while their invocation is running. Workers inspect remote invocation state before fetching pending Tools. An observed interruption fails the Run and marks the Session Runtime interrupted in one lease-fenced transaction, even if cancellation was pending: process termination has not been confirmed. A known interrupted workspace is not automatically restarted or reused. This is distinct from transport uncertainty and does not eliminate the need to reconcile already dispatched external side effects.

For an already initialized Runtime, failed private-endpoint discovery, exhausted transport retries or upstream 5xx responses change its binding to `unreachable` under the current Run lease. This records uncertainty, not process termination: the Run remains recoverable and the existing invocation/workspace are preserved. Recovery skips bootstrap/install/input delivery, resubmits only the immutable idempotent invocation, and records `runtime.reconnected` on a confirmed response. Reconnection and clearing the corresponding recovery error are fenced; terminal interruption still overrides reachability. Fleet exposes the binding state independently of the Run and last recorded Sandbox state.

Fleet returns tenant-scoped create/delete operation summaries independently of the last recorded Sandbox state. Unknown operations retain a reason and remain visible while the Session is closing. Repeating close reconciles the same resource IDs and delete operations; provider-confirmed absence completes deletion without another destroy request. Console offers a cleanup retry while preserving dependency guards on connection deletion.

Cancellation before any persisted Harness invocation does not depend on a healthy Runtime: the worker records cancellation without attempting bootstrap or remote launch. The Session retains its provider resource for explicit close and reconciled cleanup. Once an invocation exists, normal remote-process cancellation and unknown-outcome handling remain required.

Cancellation prevents new Tool dispatch, but does not retract an already dispatched remote operation. Its current leased worker may persist the eventual response or unknown outcome while the Run remains cancelling. Late unsuccessful responses emit an audit event rather than requesting authorization to resume a cancelled task. Pending approvals expire on cancellation; late decisions cannot restart execution. Lease checks continue to reject stale workers during response settlement.

Tool credential authorization may be refused per invocation through API, both SDKs and Console. The refusal shares the broker's advisory lock and locks the Run/call rows, verifies tenant scope and the immutable request hash, then persists a Tool error and audit events atomically. It never contacts the Tool or changes credentials. The broker returns that cached error on its next poll; a Run waiting for authorization returns to running. Cancellation and already-dispatched operations win over a stale refusal. Repeated refusal is idempotent and never revives a terminal Run. A later distinct Tool invocation can ask for authorization again.

Runtime cancellation captures current Linux descendant process identities before terminating the Harness, including descendants in separate process groups. It signals and, if necessary, force-stops those captured processes; terminal cancellation waits for settlement. Linux start times fence PID reuse. This is process lifecycle handling, not a security boundary against arbitrary daemonization or a request to stop unrelated Session preview services.


Associated cloud resources have their own cleanup boundary. A connector may implement `cleanupAssociatedResources(id)` for endpoints that can survive compute termination. Session close invokes it before confirming deletion, including when compute inspection returns absent. Failure keeps the same deletion operation unknown and the Session closing; retry reconciles those endpoints without blindly deleting absent compute again. Blaxel preview quota exhaustion during expanded acceptance exposed this distinction, and a dedicated database regression covers it.

Sandbox HTTP targets may own request-scoped local tunnels. `SandboxHttpTarget.release` is an internal cleanup callback; it is never serialized into the API. Runtime caches only stable targets without this callback, retains a leased target through safe retries and JSON body consumption, then releases it on success or failure. The preview proxy releases after HTTP delivery, rejected redirects, upstream failures or browser disconnect; disconnect also aborts the upstream fetch. This preserves ordinary provider URL behavior while adding ownership needed for WebSocket-to-TCP transports.

## Persistent provider deadlines

Connectors that declare `expiry: control_plane` receive a durable deadline recorded in the create operation before any remote create. Unknown-create diagnostics and reconciled resource IDs merge into that record without erasing the deadline. Bound Session resources expose `expires_at` and `expiry_enforcement: control_plane`. Provider sleep is a resource state, not absence.

Execution workers run a separate, non-overlapping expiry sweep at startup and every five seconds; a long model Run does not stop the sweep. Due Sessions first enter closing, reject new submissions/previews, revoke active Run leases, and expire pending approvals. Resource deletion follows the existing exact-ID reconciliation path. Only confirmed resource absence permits terminal cancellation and Session closure. Completed output and artifacts remain unchanged. Unknown deletion remains visible/retryable, and restarted workers resume from persisted intent; failed resources rotate behind less recently attempted resources in the sweep. This cannot enforce deletion while every control-plane process is offline; the GUI states that limitation.

Sprites uses bounded detached execs for background processes instead of replaying arbitrary commands as auto-restarting services. A unique startup marker proves the remote shell accepted the command; Runtime health separately proves Runtime readiness. SDK ExecError represents an observed nonzero exit and is normalized to the shared command result. Network failures remain exceptions/uncertainty. Idle/sleep recovery and full advertised Harness combinations require their own evidence.

Upstash uses persistent Box resources with native pause/resume and control-plane expiry. The earlier EphemeralBox TTL probe is historical evidence; the durable sweeper now enforces the active Session deadline independently while preserving sleeping workspaces. Operation names are deterministic and reconciliation is exact-name. The provider's agent runner is unused. Foreground commands have a remote GNU timeout; detached background launch closes inherited stdio and has the same remote bound, while Runtime readiness is checked independently. Request-scoped private HTTP uses authenticated exec-session stdio and the shared TCP relay. Account credentials remain in the SDK on the control plane. Because its callback API has no receive-pause or send-drain primitive, the adapter fails on more than 8 MiB queued output or 16 MiB input per tunnel connection rather than allowing unbounded buffering or dropping bytes. Normal streaming responses can exceed the output queue limit if consumed promptly. Provider sleep is never interpreted as absence, and only observed 404 establishes missing compute. Network allowlists are not advertised. Pause/resume preserves files and restarts the Runtime.

Vercel uses named persistent sandboxes with no public port routes. The control plane owns the team/project/token binding, requests a provider timeout and declares durable control-plane expiry so the named resource is explicitly deleted. Inspection does not resume compute; explicit lifecycle resume wakes the persistent instance before command/file/preview operations. Only provider 404 is absence. Exact-name list reconciliation includes the required name sort. Private HTTP reuses the stdio/TCP relay, encoding output as bounded base64 frames because Vercel command logs are text. Acknowledged stdin writes and output drain preserve backpressure; EOF and remote exit are required for successful completion. The short-lived relay has a remote deadline and explicit kill/release handling. No account credential enters the VM, and no provider route is exposed to a browser. Network allowlists and user-managed snapshots are not advertised by this adapter. Native stop/resume preserves the filesystem.

Agent37 uses the base Linux template, fixed 2 vCPU / 4 GiB resources, no public ports, disabled automatic sleep, no managed-model budget, and shared control-plane expiry. Reconciliation matches both name and operation metadata and retains ambiguity if multiple resources exist. Commands have remote GNU timeouts; file writes use bounded chunks and an atomic final rename, and reads explicitly reject truncation/incomplete chunks (64 MiB adapter read limit). The provider's authenticated edge strips the account header before forwarding it into the guest; the real probe checks this boundary. Provider auth remains separate from Runtime auth and browser preview grants. Native stop/start is supported; managed Runtime, Harness cache and workspace paths live under persistent home because `/tmp` is cleared on restart. Network allowlists are not advertised.

Agent37 reserves `/health` at its edge. RuntimeClient therefore maps its internal health request to `/_hexagon/health` and requires `{state: ready, protocol: 1}`. Runtime retains the legacy route for compatibility, but readiness no longer accepts a generic provider success response. This prevents false bootstrap/recovery health.

Freestyle uses SDK 0.2.23 and the v5 VM API, with explicit outbound-only firewall rules, no public ingress/domain, automatic restart disabled and idle pause disabled. Provider wall-clock TTL/automatic deletion are disabled; the control plane enforces active deadlines without expiring a paused workspace. The account-unique operation slug is never reassigned, and reconciliation also checks metadata. Paused/stopped resources are not implicitly executed or written. Files use SDK atomic hash-checked writes. Private HTTP uses a raw PTY over the provider-authenticated WebSocket: a unique readiness marker confirms raw mode before input, the shared relay preserves binary bytes/EOF, and every connection has bounded buffers and a remote timeout. Release kills and closes its PTY session. Provider credentials stay in the control plane. Native VM pause/start is supported; domain-allowlist capability is not advertised.


Fly Machines owns an isolated App/private network per Session, and uses the App as its durable resource ID so partial Machine creation or automatic compute destruction does not orphan the outer resource. No public service, inherited secret, volume or restart policy is configured. An empty App remains discoverable for deletion; only App 404 is confirmed absence. Commands reject non-running/ambiguous Machines. File data travels through exec stdin in bounded blocks, with atomic final rename. Private HTTP uses an exact-Machine flyctl TCP proxy (0.4.109 or newer), isolated agent, token-mode WireGuard and private temporary config. A credential-scoped lease pool reuses adjacent requests, closes after ten idle seconds, rotates at five minutes and closes on App deletion. A bounded guest IPv6 relay also supports IPv4-only user Web servers; it contains no account credential, stops on proxy close and has a 360-second fallback deadline. The earlier per-request SSH implementation passed primitive checks but timed out full tasks, so it is retained only as probe evidence. Provider credentials stay in the control-plane child environment. The control plane enforces active deadlines through durable whole-App deletion. Native suspend/start preserves disk; cold boot is handled through Runtime restoration. Proxy readiness waits for a real remote HTTP response, not just a bound local port. The real Connector/Runtime/expiry, GUI and current three-Harness dual-SDK journeys passed, with retained-record audit and confirmed cleanup.


Tool verification may include bounded account/scope display metadata from a successful authenticated JSON endpoint. Only those two fields are retained, with size/control/credential-echo filtering; raw responses are not persisted. Missing identity metadata stays explicitly unknown in Console. Connection-version validation and invalidation on configuration/credential rotation still apply. The displayed remote scope does not replace local Tool operation and approval policies.

## Boat asynchronous deletion

Boat is registered through the same SandboxConnector boundary, with no inherited account environment (`noEnv`), native snapshots enabled and a bounded active stop TTL plus control-plane deletion deadline. Its private port token stays in internal proxy headers; account API credentials never enter the guest. The current file API adapter bounds each file to 5 MiB. Native stop/resume uses the provider snapshot; the adapter treats files as durable and rebuilds Runtime processes. Egress allowlists and desktop streaming are not advertised.

Boat removes a sandbox from discovery as soon as deletion is accepted, before purge completion. SandboxConnector therefore offers optional `reconcileDeletion(id, context)`: the lifecycle supplies the durable provider operation ID and a database callback to record a new ID before polling. Boat verifies the operation target and `completed` status before confirming absence. A retry after control-plane reconstruction resumes the recorded operation. A lost DELETE response without a recoverable handle remains unknown; an early 404 alone cannot close the Session. Other providers retain their existing confirmed-absence deletion contract.

Blaxel private-preview creation uses a deterministic name per sandbox/port. Independent callers may both observe 404; a subsequent POST conflict (409) is reconciled with a GET of that exact name. The returned resource must still pass port, private-access and trusted-origin validation before tokens are requested. No duplicate POST or public fallback is used. This handles a reproduced allocation race and does not by itself prove all earlier concurrent HTTP 502 cases resolved.

## User-defined execution environment

Agent creation and Session creation accept `variables: Record<string, string>` (`env` remains a compatibility alias). These are ordinary values readable by guest code, not managed Secrets. Agent defaults are merged with Session overrides by key and frozen when the Session is created. Empty strings are values, not deletion markers. Omitted maps preserve the previous behavior. Changing env requires a new Session (and a new Agent definition when changing reusable defaults); Run submission does not mutate it.

Execution owns validation and the merge. SecretStore encrypts separate Agent and Session maps with tenant/resource/purpose-scoped AES-GCM; ordinary definitions, public responses and Fleet expose only `env_names`. The worker decrypts the Session map only when installing the Harness or constructing the encrypted, durable Run invocation. Adapter-owned invocation values take precedence. Reserved names are rejected at the API boundary.

The shared Sandbox command overlay supplies the same environment to Harness installation commands across all connector implementations. It writes JSON to the private Runtime directory, checks mode 0600, and uses a Python exec launcher; the launcher reads values from that file instead of interpolating them into its shell command or arguments. Runtime receives the Run map through its authenticated private API and applies it to the Harness process and its descendants, including tools or preview servers launched by that process. Runtime supervision and provider credentials remain outside the user map. This is process-scoped injection; provider VM creation, provider image builds and unrelated connector commands do not inherit it. No provider-native env feature is required.

The map permits at most 64 variables, names of 1–128 ASCII identifier characters, values up to 16,384 JavaScript string code units, and 65,536 UTF-8 bytes for the JSON map. NUL values are rejected. `HEXAGON_*`, `OPENCODE_*`, `PI_*`, `PORT`, `NODE_OPTIONS`, `PYTHONPATH`, `PYTHONHOME`, `LD_PRELOAD` and `LD_LIBRARY_PATH` are reserved. Host environment variables are never automatically forwarded: SDK callers explicitly select values. Agents can read their injected values, so encrypted storage and write-only API responses are not a guarantee against agent-authored output/artifact disclosure. The existing Runtime output redaction is best-effort.


## Protected credential access

ManagedSecrets owns tenant-scoped write-only resources and reference-aware rotation. Connections bind resources to provider configuration or exact HTTPS request policies. ConnectionAccess owns hashed, expiring Session/Run grants; the dedicated access listener authenticates each request, applies fixed upstream credentials and streams bytes using Undici. It does not interpret model payloads, select models, retry upstream actions or implement billing. Disabled/deleted resources, changed versions, ended Runs and closed Sessions deny subsequent requests.

All Sandbox connectors support the shared external proxy path. Vercel additionally applies persisted native Header transforms for delegated grants; the worker strips native metadata before Runtime delivery. The original upstream secret stays in the control plane in both modes. Other vendors' native Secret APIs are not claimed as implemented. A failed native policy update does not downgrade to guest token delivery. See [the API, deployment contract and limitations](secret-management.md).

## Instabox provider boundary

Instabox implements the shared SandboxConnector with HTTPS lifecycle/file/command APIs and request-scoped OpenSSH certificate tunnels for Runtime and previews. Account keys stay in the control plane; new machines explicitly opt out of Vault and native Secret delivery. The existing external credential proxy serves protected model and HTTP bindings. Native scheduled deletion and control-plane expiry reconciliation are both used. See [Instabox](instabox.md) for host prerequisites, unsupported capabilities and acceptance.

## Personal application adapters

`integrations/apps/` owns fixed provider request mappings and operation schemas. `modules/apps/oauth.ts` owns tenant-scoped OAuth client registrations, consent transactions and encrypted token refresh. `modules/tools/adapters.ts` selects application or generic HTTP execution; `ToolBroker` remains the shared authorization, approval and uncertain-outcome journal. Sandbox connectors and Harnesses have no application-specific credential handling. See [application connectors](application-connectors.md) for exact delivered providers, API contract, consent setup and remaining scope.

## Product completion boundaries (2026-11-16)

- `modules/deployment` owns local deployment configuration, revision-conflict protection, outbound transport initialization and development ingress status. The management server starts independently of tunnel success. `tooling/local.ts` applies persisted configuration before spawning the control plane; explicit environment overrides are documented in `docs/local-installation.md`. Hosted mode requires explicit database, encryption, identity and stable ingress configuration.
- `agents` are reusable definitions with immutable revision history. Updating a definition increments its revision under a row lock. A Session pins the chosen revision and connection configuration; archiving only blocks new Sessions. Definition-only preflight shares the Session checks without creating an Agent or cloud resource.
- Application API tokens use hashed values, expiry, last-use tracking, atomic rotation and revocation. They execute configured work; owner credentials retain configuration, approval and administrative authority. This is a local/workspace boundary, not a general organizational RBAC system.
- `modules/execution/queries.ts` supplies tenant-scoped paginated Sessions, Runs, overview and pending work. `modules/sandboxes/operations.ts` supplies operator reviews; acknowledgement retains `unknown` and never asserts cleanup. Provider reconciliation is serialized per Session and backs off into manual review. Provider-accepted asynchronous create handles can be persisted before polling via `SandboxRequest.record`.
- Console modules own page-level interactions: `agents`, `infrastructure`, `operations`, `tokens`, `quickstart`, `run-detail`; shared accessible controls remain in `components`. `session-code` and `http-code` generate executable recovery examples, tested against the actual SDK contracts. Journals contain input and identifiers but no API token; an exclusive local journal lock prevents accidental concurrent submissions.
- Sandbox capability declarations and evidence are separate: supported interfaces are adapter capabilities; historical account/resource verification does not prove present quota, connectivity or every permission. SaaS adapters without real account authorization remain explicitly contract-tested only.

## Direct Session API (2026-11-17)

POST /v1/sessions and /v1/sessions/preflight accept either a harness definition directly or a legacy agent_id, never both. The direct request includes sandbox_connection_id, model_connection_id, optional name/resources/network/required_capabilities, optional tools (binding name → connection ID), optional_tools and env/variables. Tools are required at initialization unless listed in optional_tools. No hidden Agent row is created. Sessions pin a validated definition and connection versions; direct sessions have null agent_id/agent_revision. Tenant ownership, capability checks, credential isolation and cloud lifecycle are shared with the existing path. Python create_session and TypeScript createSession expose the same request. Agent registration remains optional reuse, not an initialization prerequisite.

## Automatic credential ingress readiness (2026-11-17)

Default local deployment reads saved deployment settings for both managed and direct startup and owns Cloudflare credential-listener ingress automatically. Session preflight/create and Worker execution await a shared readiness coordinator. An unavailable/stopped channel is restored once for concurrent callers, then checked against this listener's instance ID before provisioning. Origin changes invalidate the health cache. The Worker repeats readiness before cloud provisioning, covering a channel stopped between Session creation and Run submission. A failed bounded startup yields a sanitized 503 (or terminal Run failure) before creating a new cloud resource. Python's default HTTP timeout is 90 seconds to cover the bounded 60-second tunnel startup plus health checks.

Recovery can replace a development origin only when no nonterminal Run has a persisted invocation. Idle sessions may continue: new invocations receive current scoped credential access. Existing in-flight invocations are never silently rewritten or replayed. Explicitly disabled ingress and hosted/external HTTPS deployments do not start a development tunnel. Network settings remain operator diagnostics; normal SDK usage does not require a manual retry. Provider keys still stay in the control plane, and only the dedicated credential listener is exposed.

## Local identity and workspace discovery (2026-11-18)

Local, explicitly loopback-bound control planes expose POST /local/connect. It requires a direct loopback peer, a loopback Host matching the bound port, an exact same Origin, Sec-Fetch-Site: same-origin and X-Hexagon-Local: 1. No CORS allowance is provided. The no-store response contains a random process-local browser credential, never the disk owner token. Protected routes validate that credential only on loopback; normal Bearer authentication remains unchanged. Hosted or network-bound servers never expose bootstrap. Console connects automatically on load and renews its browser credential after an authorization failure following service restart. Local Console does not show manual token onboarding or logout as a required lifecycle step.

Startup publishes private, atomic connection.json in the data directory and a discovery pointer at ~/.hexagon/local.json (overridable via HEXAGON_LOCAL_DISCOVERY_FILE). Both SDKs expose local(): explicit data directory, HEXAGON_DATA_DIR, project-ancestor .local/control-plane, then home pointer. They verify private file permissions/current owner, loopback-only HTTP origin, optional expected port and local-workspace identity before reading and using the owner credential. Local processes inherit the OS user's existing ownership; neither passwords nor tokens are entered manually. Browser SDKs and remote/hosted clients retain the explicit authenticated constructor. Tests use isolated discovery pointers to avoid replacing the user's active workspace.

Harness images are registered through `/v1/harnesses` and pinned to verified OCI digests. Runtime adapters translate execution protocols; Sandbox connectors own image provisioning and lifecycle. See [Harness images](harness-images.md) for contracts, provider boundaries and SDK migration. Legacy source packages remain readable for existing sessions.

## Model wire protocols (2026-11-18)

Connections distinguish `anthropic-compatible` (Messages) from `openai-compatible` (Chat Completions) and `openai-responses` (Responses). The control plane validates a bounded request in the chosen protocol. ConnectionAccess allows only that protocol's POST path and injects the corresponding header; response bodies and SSE pass through unchanged. The worker passes the pinned provider identifier to the Harness adapter. OpenCode and Pi choose their native protocol implementations. No conversion, routing or fallback between model APIs is performed. New OpenCode/Pi OCI registrations advertise all three protocols; existing immutable registrations retain their declared capability snapshots.


## Remote tool protocols

The control plane's MCP adapter uses the official TypeScript MCP client for Streamable HTTP and legacy SSE. Connection discovery is tenant-scoped and compare-and-swap fenced. Selected tool schemas are pinned in Session bindings; discovery produces a disabled revision requiring review and revalidation. The broker handles external MCP calls through the same durable tool-call/approval protocol as applications. It never assumes that an untrusted read-only annotation makes a tool safe to auto-approve. See [Remote MCP](remote-mcp.md).

Feishu/Lark extend application authentication with a control-plane token exchange hook. This remains orthogonal to Sandbox connectors and Harnesses. Provider credentials and exchanged tokens are never delivered to the guest. The Sandbox receives only selected tool schemas and a scoped mailbox grant.

## Initialization observability

`GET /sessions/:id/initialization` exposes a versioned, tenant-scoped historical projection of the persisted Session definition. Console and both SDKs use it without consulting current Agent/connection configuration or decrypting secrets. New Sessions capture connection names and protected API aliases; older Sessions retain their original snapshots and persisted binding rows. Environment names are observable; values are not. Conversation/resource views remain responsible for current state. See [Session initialization](session-initialization.md).

## Local distribution and recovery boundary

`tooling/build-local.ts` emits compiled control-plane code, runtime assets, Console assets and both local SDK distributions. Its generated launch commands use Node directly; production installation excludes TypeScript/tsx/Vitest. Host PostgreSQL and cloud Sandbox providers remain external dependencies. The source checkout and compiled distribution use the same deployment settings and data directory contract.

Local credential ingress has a single coalesced readiness operation shared by startup, SDK creation and worker preparation. An enabled channel is checked in the background, with bounded backoff and sanitized health metadata. Transient probes are rechecked before replacement. An origin referenced by a nonterminal persisted invocation cannot be rotated; recovery must preserve that invocation rather than replay its external effects. This handles an idle channel process failure, but cannot guarantee availability of a third-party tunnel or a sleeping host.

Offline backup requires a stopped local service and closed Sessions. A schema-scoped PostgreSQL dump travels with its matching encryption key, owner identity, optional deployment settings and file hashes. Restore accepts only an empty database/data directory, validates the owner against its tenant, decrypts every retained secret and regenerates runtime discovery on startup. Migration checksums prevent modification of previously applied migrations; unknown applied versions fail closed. Backups are trusted private artifacts, not portable untrusted uploads or a live migration mechanism.

OpenClaw 2026.11.5 activity observation subscribes to its actual public event bus from the pinned image. The preload survives the CLI's own Node respawn. It emits bounded tool start/result metadata only; arguments, outputs and reasoning are excluded. The terminal CLI JSON remains authoritative for completion. Custom images without that upstream event bus retain final-result execution and report observer unavailability in runtime diagnostics.

## Application authorization evidence and refresh fencing

CRM/application validation separates local allowed operations from provider-reported scopes and per-operation permission evidence. No write probe is permitted. Sessions pin a verified remote account identity when available, and ToolBroker rejects identity changes. Local credential disconnect invalidates policy versions and removes connection envelopes; provider revocation remains separate.

OAuth refresh uses a durable attempt keyed by tenant, connection and encrypted grant ID. Intent commits before HTTP; a successful replacement requires the same connection version, grant reference and client ID. The remote request holds no database transaction. A lost response/crash leaves an uncertain attempt, preventing replay of a potentially rotated refresh token. SDK/Console authorization state surfaces uncertainty and reauthorization. Existing grants without client-ID binding require reauthorization. See docs/application-connectors.md.

## Serverless Session wake and native idle sleep — 2026-11-19

A Session is a durable conversation identity, not the lifetime of an executing Harness process. New messages may be accepted in open, paused, pausing or resuming state. Run submission persists once under the existing idempotency key; the worker wakes/reconciles the Session before Runtime access. The API does not require clients to resume first. Closing/closed remain terminal for new messages. One nonterminal Run per Session remains the concurrency contract.

Session lifecycle events persist pausing/paused/resuming/resumed transitions separately from Run events. Pause takes the Session row lock used by submission and requires no nonterminal Run. Native cloud mutations use the same advisory lock as provisioning and close, commit intent before remote calls, inspect the exact resource after a lost response, and never blindly replay uncertain mutations. Worker retry and the idle sweep reconcile transitional states.

E2B, Freestyle and Instabox expose memory-preserving pause/resume. Vercel, Upstash, Boat and Agent37 expose persistent filesystem resume; Fly Machines may restore memory or cold-boot, so Hexagon treats disk as authoritative. Modal uses native filesystem snapshots and may replace the underlying Sandbox ID while retaining the Session ID. A background idle sweep sleeps eligible workspaces after resources.idle_timeout_seconds (default 60, minimum 15, capped ten seconds below the active timeout). Confirmed native sleep does not expire merely because its previous running lease elapsed. Wake records a new bounded running deadline before resuming. Logical Session sleep alone does not stop compute or suspend expiry. Running tasks retain the configured resource safety timeout.

Blaxel and Sprites delegate standby to the provider (`automatic_standby`), without pretending that an idle timer proves compute suspension. Blaxel control API reports DEPLOYED for both active and standby; background Runtime/preview helpers must not request keepAlive. Sprites may resume warm memory or cold-boot with persistent files. Public preflight distinguishes `serverless`, `provider_managed` and `retained`, and declares the preservation mode. A provider-managed sleeping Session does not report `compute_paused: true` without provider confirmation.

Filesystem resume marks the Runtime binding `restoring` before committing the wake. Reprepare/relaunch preserves the native conversation ID, installed Harness cache, workspace, prior Run records and inputs; it must not replay initial input uploads. The supervisor owns an exclusive file lock so warm providers cannot create a second listener. Providers that clear `/tmp` keep Hexagon-managed directories under a persistent guest directory and recreate only their compatibility links on resume. Arbitrary guest temporary files are not part of the managed workspace guarantee.

Modal checkpoint and restore operations persist intent before cloud mutation. Snapshot identity is stored before terminating source compute. A lost snapshot outcome remains review-required; a lost restore response is reconciled by its unique operation name. Close reconciles all source/restored resources and deletes recorded native images. Native snapshot retention still applies (Modal's default snapshot TTL is 30 days); this is not indefinite storage. Never silently replace an unplanned lost/incompatible workspace or replay an active invocation under the claim of resuming it. Active previews do not count as Agent tasks; a sleeping workspace must wake before preview access.

Activity is computed from tenant-scoped persisted Runs across the full workspace, independently of list pagination: distinct Session IDs overlapping each rolling bucket. It represents task activity, not HTTP request count or provider CPU utilization.

## Provider-owned OCI preparation

Connectors may prepare an OCI image into a provider-native execution template. E2B uses this path; direct-image providers retain their existing path. Preparation runs under the Session lifecycle lock and writes a distinct image_prepare operation before starting the remote build. Template/build receipts precede polling and Sandbox creation has its own operation. A known building result defers the worker lease and emits one durable sandbox.image_building event without marking the Run as failed or uncertain. Unknown remote outcomes reconcile only; an absent result is not permission to submit a new build. Session close deletes compute before its owned template and cannot complete while template cleanup remains unconfirmed. The first implementation is Session-scoped with no shared template cache.
