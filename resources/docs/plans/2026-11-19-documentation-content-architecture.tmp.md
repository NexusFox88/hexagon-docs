# Hexagon 开源文档内容架构与逐篇写作任务书

> 临时设计稿 · 2026-11-19 · 用于内容评审与任务拆分，尚未实施为网站导航。本文提出的是目标内容架构；列出的页面、自动生成能力和质量门禁不代表已经存在。产品事实必须在写作时按目标版本复核。本次只编制文档，不修改产品行为，不提交或发布。

**如何阅读和使用本稿**

- **评审产品方向**：先读第 1—2 节，确认定位、读者、成功标准和参考取舍。
- **评审内容架构**：读第 3 节的导航、首页和用户路径，再读第 6—7 节的事实来源与现有文档迁移安排。
- **分派具体写作**：直接使用第 5 节的 82 项任务书；每项的专有要求与第 4 节的全站编辑契约共同构成写作要求，不能只按标题写文章。
- **决定交付顺序**：按第 8 节的旅程闭环安排批次；按第 9—10 节检查发布条件，不能把目录齐全视为内容完成。

本稿的核心决策是：以“评估 → 首次成功 → 接入应用 → 长期运行 → 扩展贡献”为阅读主线，以版本化参考、可运行示例和有范围的证据作为共同基础。七个导航栏目服务这条主线；82 项资产是写作拆分，不要求一次上线，也不要求每项都独立成网页。

## 1. 内容战略：文档要帮助用户完成什么

### 1.1 产品价值主线

建议文档统一使用下面的定位作为编辑基线，再通过真实旅程验证措辞：

**Hexagon 是可自托管的开源 Agent 控制平面，让应用通过一致的 API 和 SDK，在可选的云 Sandbox 中运行、观察和管理有状态的 Agent 任务。**

这句话应展开为四个可观察的结果，而不是四组功能名称：

1. **接入应用**：应用创建 Session、提交任务，并拿到可以继续查询的 Run、事件和产物。
2. **组合执行环境**：在兼容性允许的范围内选择 Sandbox、Harness、模型和 Tools；变更组合时保留共同的应用接入方式。
3. **处理真实任务生命周期**：支持多轮工作、工具授权与审批、断线重连、取消、空闲休眠和资源清理；对不确定结果提供调查与对账路径。
4. **掌握部署与凭据边界**：自行运行控制平面，配置自己的云资源与模型连接，理解哪些凭据留在控制平面、哪些数据会进入 Sandbox。

文档不能把“统一接口”写成“所有组合等价”，不能把“有状态”写成“内存和进程永不丢失”，不能把“可自托管”写成“任务默认在本机执行”。当前 local / hosted 指控制平面的部署位置；真实端到端验收使用云 Sandbox。

### 1.2 文档承担的五个产品职责

| 职责 | 用户需要得到的答案 | 文档交付的证据 |
| --- | --- | --- |
| 评估价值 | 为什么需要 Hexagon，是否适合我的应用？ | 一句话定位、具体场景、边界、可运行结果 |
| 建立信任 | 这些能力到底支持到什么程度？ | 版本化接口、能力矩阵、真实验证范围、限制与已知问题 |
| 完成激活 | 如何第一次创建 Session 并拿到结果？ | 最短完整教程、预期输出、清理方法 |
| 扩大使用 | 如何把一次演示接入自己的产品？ | 后端接入、事件 UI、审批、产物、恢复等任务指南 |
| 形成贡献 | 如何安全地扩展和维护这个项目？ | 系统边界、开发环境、扩展契约、测试与贡献流程 |

优先优化“完成一项工作所需的信息是否齐全”，而不是页面数量。内容目录可以完整规划，但未达到发布条件的页面留在写作看板，不在公共侧栏放占位页。

### 1.3 读者与成功标准

| 读者 | 起点问题 | 核心路线 | 结束时应能证明 |
| --- | --- | --- | --- |
| 首次评估的开发者 | 它解决什么问题？ | 首页 → 产品介绍 → 首个 Session | 有一个真实 Run、可读结果、已确认的资源清理 |
| 应用开发者 | 如何把 Agent 放进我的产品？ | 后端接入 → 多轮 → 事件 → 审批 / 产物 → 恢复 | 应用能够保存标识、恢复观察、处理失败，且不会把管理凭据交给浏览器 |
| 平台 / 运维工程师 | 如何可靠地长期运行？ | 自托管 → 网络 → 身份 → 监控 → 对账 → 备份 | 能识别故障层次，恢复服务并核对云资源 |
| 集成开发者 | 能不能使用我的 Provider / Harness / Tool？ | 组合选择 → 具体接入页 → 矩阵 → 扩展契约 | 明白接口支持、实际验证和缺口分别是什么 |
| 开源贡献者 | 如何做一个可审查的变更？ | 开发环境 → 代码地图 → 扩展 / 测试 → 提交流程 | 能运行相关检查，并交付符合边界的代码和文档 |
| 编程 Agent | 如何准确调用与排查？ | Agent 阅读入口 → 版本化参考 → 完整示例 → 错误 / 恢复 | 使用真实契约，不猜测字段、不盲重试远程副作用 |

Console 是配置和观察工具，SDK / HTTP 是应用接入主线。文档不能把 Console 截图操作当作完整的产品集成教程，也不能让用户在掌握首个任务前读完内部模块说明。

## 2. 参考取舍与架构升级

### 2.1 从 GoBare 采用什么

参考已阅览的 [GoBare 文档首页](https://docs.gobare.dev/)、[Quickstart](https://docs.gobare.dev/quickstart)、[Production integration](https://docs.gobare.dev/production-integration)、[Approvals guide](https://docs.gobare.dev/guides/approvals-in-your-product)、[Troubleshooting](https://docs.gobare.dev/troubleshooting) 和 [Agent 阅读入口](https://docs.gobare.dev/AGENTS)。以下为内容设计启发，不是对其实现或测试系统的审计结论。

| 可借鉴做法 | Hexagon 的具体落点 | 必须增加的内容 |
| --- | --- | --- |
| 首页迅速展示价值和完整调用结果 | 首页给出一个 Session → Run → 结果的短例子 | 自托管控制平面与云 Sandbox 的部署图 |
| 上手教程完成一个闭环 | 首个 Session 以结果、持久查询和清理结束 | 连接验证、启用和组合兼容性前提 |
| 每页注明何时阅读 | 页面摘要直接写“当你需要……时阅读” | 先决条件、版本、适用组合与证据范围 |
| 单独解释从演示到应用集成 | 设置“将 Agent 接入你的后端”桥接指南 | 应用身份映射、持久标识、幂等、流恢复与资源归属 |
| 按具体任务组织指南 | 审批、产物、流式 UI 等独立任务页 | Hexagon 的授权、执行、Sandbox、Runtime 状态区别 |
| 用成功条件结束文章 | 每篇教程有“完成后应看到什么” | 同时验证失败分支和清理，不只看最终文本 |
| 为编程 Agent 提供阅读入口 | 稳定路径、机器可读参考与 Agent 指南 | 能力发现、版本约束、未知结果对账要求 |

不沿用其他产品的语义：Hexagon 的 Session 是持久工作上下文，不能直接等同某一台云计算机；单个 Session 当前只允许一个活动 Run，不能承诺忙时自动排队；产物与终态的顺序必须符合 Hexagon 的真实契约。其他产品的公开应用发布、Webhook、回调或多 Agent 功能，不自动成为 Hexagon 的文档栏目。

### 2.2 内容类型与用户导航分开

采用 [Diátaxis](https://diataxis.fr/) 的教程、操作指南、概念解释、参考四类内容作为内部编辑分类；公共导航使用用户任务语言。借鉴 [Temporal 文档](https://docs.temporal.io/) 对开发和部署路径的区分，以及 [Docker 文档](https://docs.docker.com/) 的任务入口组织方式。

同一主题允许有不同类型页面，但每页只承担一个主要责任。例如：

- “创建首个 Session”教用户走通一个固定例子。
- “在多轮任务中继续工作”解决应用中的连续任务问题。
- “Session、Run 与 Agent 模板”解释对象语义与生命周期。
- “Sessions API”精确定义字段和响应。

四页互相链接，字段表只维护在参考页，机制说明只维护在概念页。教程不复制全量字段，参考页不承担教学叙事。

### 3.2 层级和展开规则

- 默认先展示用户所在栏目；Provider 叶子页面收在 Sandbox 子组，避免首次访问出现几十个选项。
- 初期可以在同一个文档应用中使用侧栏分组，不要求为了七个栏目建设复杂门户。
- 页面最多经历“栏目 → 子组 → 文章”三级导航。某个功能只存在一份规范解释，其他位置链接过去。
- API 与 SDK 参考由对象索引和成员锚点组成；确有内容体量需要时再拆页，不按内部源文件切页。
- 不建立空的 Overview 页面。需要总览时，必须提供决策、对象关系或任务索引，不能只有链接列表。
- 正式版、实验能力、未来提案在页面状态上区分；历史证据保留时间和范围，不混入最新教程步骤。

### 3.3 首页六个内容区块

1. **产品价值**：一句话定位、一个真实适用场景；主按钮“创建第一个 Session”，次按钮“查看完整应用示例”。
2. **可见的完成结果**：短代码与对应结果，展示 Session ID、Run 终态和一个产物；不要用伪造日志冒充执行记录。
3. **三类常见工作**：接入 Agent 后端、运行项目任务、管理多种执行组合；每个场景只链到一个主指南。
4. **一张部署图**：应用 / Console → 控制平面 → 云 Sandbox 内 Runtime / Harness；模型和 Tools 标明调用与凭据边界。
5. **按目标继续**：“我要试用”“我要接入应用”“我要自托管”“我要贡献”。
6. **兼容性与可信度**：链接能力表、已验证组合、限制和更新记录；不在首页手工复制会过期的组合总数。

### 3.4 两层上手体验

**第一层：最小成功。** 启动控制平面 → 配置并验证一个 Sandbox 和模型连接 → 直接创建 Session → 提交 Run → 读取结果与产物 → 关闭并确认清理。优先选择有完整双 SDK 证据的固定组合。读者不必先创建 Agent 模板，也不必先接 OAuth 或 Tools。

**第二层：真实价值。** 上传一个小型 Web 项目 → Agent 修改代码并运行固定测试 → 私有预览 → 下载产物 → 同 Session 继续一轮 → 关闭并再次读取历史结果。工具授权和人工审批通过后续任务指南加入，避免一次上手塞入所有分支。

“五分钟上手”只有在目标用户、干净环境和真实云资源上测量过才使用。安装时间、云启动时间、模型延迟应分开观察。

### 3.6 顶层设计的决策依据与扩展规则

这套架构追求的是：用户在每个阶段都能找到下一步，作者知道每条事实由哪里维护，维护者能判断一次产品变更影响哪些文章。栏目数量不是目标；下面的决策用于在内容增长时保持结构稳定。

| 设计决策 | 解决的读者问题 | 内容归属与取舍 |
| --- | --- | --- |
| 以用户任务作为一级导航 | 用户知道自己想完成什么，但未必知道内部模块名称 | 开始使用负责首次成功，构建应用负责业务集成，部署与运维负责持续运行；代码模块只在贡献栏目展开 |
| 连接与兼容性独立成栏 | 用户需要判断手上的 Provider、Harness 和模型能否组合 | 集成页写供应商特有前提，公共流程留在任务指南，组合结论集中到已验证组合；不在每个教程重复矩阵 |
| 概念与参考分别维护 | 用户既需要理解机制，也需要查精确契约 | 概念回答为什么和边界，参考回答字段、权限、状态和错误；同一个事实只指定一处规范来源 |
| 上手分成最小成功与真实项目两层 | 第一次体验需要短路径，评估实际价值需要完整工作流 | S04 固定一个组合完成结果与清理，S06 验证文件、测试、预览和连续任务；不把所有功能塞入首个教程 |
| 应用接入设置专门桥接页 | SDK 调用成功后，开发者仍需解决身份、持久化和恢复 | B01 串起应用职责，再链接专题指南；不能让读者从接口参考自行拼出生产接入方案 |
| 证据作为横贯所有栏目的内容属性 | “可以配置”不等于“这个版本和组合已验证” | 文章就近展示影响使用的限制，详细执行记录归入维护材料；禁止以一次成功外推全部组合 |
| 人与编程 Agent 使用同一套规范内容 | 两套独立说明容易出现字段、版本和行为差异 | Agent 入口负责阅读顺序和稳定链接，机器可读输出从同源内容派生，不另写一套产品契约 |

**新增文章的判断顺序：** 先写出读者的唯一主要问题，再查现有资产是否已有规范责任。若只是新的参数或供应商差异，优先补充参考或集成页；若存在独立的前提、操作过程和成功判据，再建立任务页。每个新页面必须确定上游入口、下游行动和事实来源，避免只能通过搜索偶然找到的孤立文章。

**内容重叠时的裁决：** 教程保留跑通所需的最小解释，操作指南保留完成目标所需的决策，概念页保留机制和反例，参考页维护完整契约。允许为阅读连续性作简短概述，但必须链接规范页；状态枚举、字段默认值、能力矩阵和版本限制不手工复制维护。

**对外呈现与内部治理分开：** 读者首先看到目标、操作、结果和影响使用的限制；作者使用任务编号、来源文件、验证记录和审稿状态。内部治理信息支持准确交付，不应占据正文主线。82 项资产是维护粒度，最终网站页数可按阅读体量调整，拆分或合并时保留任务覆盖映射。

## 4. 全站编辑契约

### 4.1 每篇文章的必填信息

每页开头给出：一句话回答、何时阅读、适用版本 / 能力、先决条件。正文根据类型组织，结尾给出可验证的完成条件和最多三个明确的下一步。

建议内容元数据如下；这是待建设的内容模型，不是已有实现：

```yaml
id: B04
title: 将 Run 事件显示到你的应用
description: 从持久事件构建可恢复的任务进度界面。
kind: how-to
audience: application-developer
status: draft
product_version: to-be-verified
canonical_path: /build/stream-events
source_files: []
example_path: null
verification: none
verified_at: null
tested_combinations: []
owner: to-be-assigned
translation_of: null
```

`verification` 应区分 `none`、`contract`、`simulation`、`real-cloud`；具体检查可以多条记录，不将四者当作一个简单线性等级。`tested_combinations` 需要包含 Sandbox / Harness 版本或 digest / 模型端点与协议 / SDK 版本 / 测试范围，禁止只写“已测试”。

### 4.2 不同类型的写作要求

| 类型 | 必须包含 | 应避免 |
| --- | --- | --- |
| 教程 | 固定环境、完整步骤、预期结果、失败出口、清理、后续路线 | 大量选项让新手自行组合；半段代码依赖隐藏步骤 |
| 操作指南 | 一个明确目标、前提、完整方案、关键取舍、常见失败、成功判据 | 按 API 列功能；通篇只讲机制 |
| 概念解释 | 问题、对象关系、生命周期 / 时序、边界、一个反例 | 把实现文件顺序当理解顺序 |
| 参考 | 精确类型、默认值、约束、权限、状态、错误、版本 | 含糊承诺；过度教学；复制多份规范 |
| 集成页 | 接入前提、配置字段、能力、验证路径、限制、清理、证据 | 把供应商文档重抄一遍；把 recipe 当真实验收 |
| 运维手册 | 触发症状、诊断、操作、风险、完成信号、无法恢复时的处理 | 没有资源归属信息就删除；没有备份就指导迁移 |

### 4.3 示例与安全边界

- 应用级指南默认提供 Python / TypeScript 对等示例；HTTP 参考提供 curl。涉及同一端到端旅程的两套 SDK 必须独立验证，不能由一套成功推断另一套成功。
- 代码来自可运行示例或真实契约，展示 import、客户端初始化、必要输入、调用、观察和清理；占位符清楚标记。未验证的函数名不提前写成可复制代码。
- 示例输出区分“实际记录”“脱敏记录”“示意输出”。截图不得暴露凭据、用户数据和私有资源标识。
- 应用凭据、管理凭据、Provider 凭据、模型凭据、Tool 凭据分别说明。Provider 凭据保留在控制平面；用户主动放入 env / variables 的值可能被 Sandbox 内代码读取。
- 事件断流不是 Run 取消；网络超时不是资源不存在；取消不是撤回已发生的 Tool 副作用；unknown 不是 failed。
- local 自动发现只适用于对应本地工作区与客户端上下文；hosted 使用明确地址和适当 Token。浏览器不得持有控制平面管理凭据。
- 清理要核实云资源与关联端点的真实状态。仅停止本地进程不能证明 Sandbox 已删除。
- 外部 API 副作用示例使用可撤销或专用测试记录，写明去重和对账方式；不以盲重试“提高成功率”。

### 4.4 发布前需要消除的现有歧义

1. 旧文档中的“必须先创建 Agent”改为“直接 Session 为主线，Agent 模板可选”。
2. 本地启动鉴权示例对齐当前自动发现机制；不能保留已过时的手工复制 owner token 主路径。
3. 能力声明与真实验证分表呈现；不把某个模型端点的协议成功外推为所有端点成功。
4. OCI Harness、内置 Harness、source package 三种路径分清，不把镜像模板存在写成真实云端可运行。
5. serverless 的文件、对话、进程和内存连续性分别描述；Provider managed idle 与平台显式暂停分清。
6. 验收文档中的历史状态与最新结论可能并存。编辑需要追溯时间和证据范围，不能摘一段旧结论当当前总状态。
7. 历史成功清理不等于当前全局无孤儿资源；公共文档给出机制与范围，不传播未经复核的“全部成功”。

### 4.5 每篇文章的写作交付模板

第 5 节的任务书应按下面的模板展开为可审阅正文。作者可以调整叙述顺序，但不能遗漏适用范围、结果判断和事实来源；概念页不必硬塞操作步骤，参考页不必编造教学故事。

| 交付项 | 作者需要填写的具体内容 | 审阅判断 |
| --- | --- | --- |
| 读者与问题 | 对应读者、阅读触发场景、本文唯一主要问题 | 标题和首段能让读者判断是否需要阅读 |
| 一句话答案 | 先给结论或完成后的结果，再展开机制 | 不以背景介绍或内部模块列表开场 |
| 前提与范围 | 版本、权限、连接、能力、依赖文章及必要输入 | 从前置页面进入后没有隐藏步骤 |
| 正文骨架 | 教程按步骤；指南按任务决策；概念按关系与边界；参考按规范对象 | 一个主要内容类型贯穿全文 |
| 核心例子 | 可运行文件路径、输入、调用、结果；解释页提供具体情境和反例 | 例子能证明主题，示意代码明确标识 |
| 失败与恢复 | 本任务最常见或后果最重的失败、观察信号、恢复动作 | 不把重试、重新创建或删除资源作为通用答案 |
| 完成判据 | 可观察的状态、内容或外部结果，以及必要的清理结果 | 读者无需作者协助即可判断完成与否 |
| 后续行动 | 最多三个与当前完成结果相关的下一步 | 不用全站链接列表代替阅读路径 |
| 审阅附件 | 事实来源、检查命令及实际结果、验证范围、待解决问题 | 区分正文承诺与尚未验证的编辑假设 |

写作任务完成时，应同时交付正文、关联示例和审阅记录。未达到某项要求时写出具体缺口，保持草稿状态；“有标题”“有代码片段”“链接检查通过”都不等于文章完成。审阅记录属于维护材料，不必全部展示给最终读者，但影响使用的限制必须进入正文。

不按统一字数配额写作。S04 应让读者沿一条路径完成任务；R01 应完整覆盖公共契约。只有当一页承担多个独立问题、读者必须反复跳过无关前提时才拆页；拆页后保留明确的规范归属和阅读衔接。

### 4.6 将任务书落实为正文：三篇示范大纲

以下大纲规定叙事顺序和交付深度，供作者展开第 5 节的任务书。它们属于写作设计，不是已执行的操作记录。其他文章按自己的主要问题调整，不机械复制教程结构。

| 文章 | 建议正文顺序 | 必须交付的具体材料 | 审稿时重点拒绝的问题 |
| --- | --- | --- | --- |
| S04 · 第一个 Agent Session | 完成后的结果 → 账户与环境前提 → 验证并启用连接 → 创建 Session → 提交与观察 Run → 核对回答和产物 → 关闭并确认清理 → 失败出口 → 下一步 | Python、TypeScript 各一个完整入口文件；明确的版本与组合；固定输入及可核对的文件内容；脱敏的预期结果；保存资源标识的方法；各自真实执行和清理记录 | 用户需要自行拼接散落片段；只打印模型回答；省略连接启用；把进程退出视为云资源已清理 |
| B01 · 接入你的后端 | 应用需要负责什么 → 身份与资源归属 → 保存 Session、业务请求和 Run → 首次提交 → 重复提交与响应丢失 → 查询和订阅 → 用户离开后的执行 → 关闭与后台对账 → 集成检查表 | 一张应用与控制平面的职责图；最小持久化数据模型；请求输入、幂等键和 Run ID 的关联例子；正常与丢失响应两条时序；凭据放置说明 | 用进程内字典冒充持久化；把租户隔离等同于应用用户授权；每次重试生成新幂等键；把连接断开等同于取消 |
| O11 · 按症状排查 | 选择症状 → 收集最小诊断信息 → 定位故障层 → 执行有前提的恢复动作 → 确认恢复和清理 → 仍未解决时提供什么 | 按连接、初始化、模型、Tools、事件、预览、清理分组的症状索引；每项写明观察信号、可能原因、确认方法和动作；至少一个完整故障案例；脱敏诊断模板 | 没有证据就断言根因；所有失败都建议重启；未知创建结果直接新建；要求用户公开凭据或完整私有任务内容 |

**审稿采用两次不同的阅读。** 第一次按读者路径阅读：假设只完成前置页面，检查是否知道下一步做什么、在哪里操作、如何判断结果。第二次按事实来源阅读：逐项核对接口、状态、权限、持久化与副作用，检查示例和证据是否支持正文承诺。文字流畅不能抵消事实缺口，检查通过也不能抵消任务路径断裂。

内容任务的交付记录使用下列格式；只有已经发生的检查才填写结果：

```text
内容 ID / 标题：
目标读者与唯一主要问题：
正文路径 / 语言 / 对应版本或 revision：
前置页面 / 完成后的下一步：
事实来源（路径、符号或官方链接）：
关联示例与运行前提：
实际检查（命令、结果、日期、证据路径）：
未验证范围与尚存缺口：
编辑审阅 / 工程审阅：待指定或实际记录
状态：草稿 / 待审 / 待验证 / 可发布
```

“可发布”要求满足第 9.1 节，而非填写完模板。已有草稿和生成的参考页仍需逐项审阅；本架构稿描述目标与要求，不替代实施台账。

### 5.4 连接与兼容性

## 6. 内容组织与单一事实来源

### 6.1 三层内容，三个不同用途

| 内容层 | 放什么 | 对读者的承诺 | 建议管理位置 |
| --- | --- | --- | --- |
| 公共用户文档 | 教程、任务指南、概念、参考、运维、贡献入口 | 对指定版本可执行、可核对 | 未来站点内容目录，按第 3 节组织 |
| 工程设计记录 | 架构细节、ADR、研究取舍、实施计划、历史演进 | 保留背景和决策，不自动代表当前用户契约 | 现有 `docs/` 设计文件及 `docs/plans/`；实施时再决定目录迁移 |
| 测试与证据 | 旅程、矩阵、实际结果、未决事项 | 说明某次验证覆盖什么 | `testing/`；敏感资源标识留在私有本地证据 |

公共文档可以链接经过脱敏和审核的设计 / 验证摘要，但不将内部文件目录原样当用户侧栏。完整失败历史应保留在工程证据中；公共指南必须明确当前操作步骤，不能要求用户从追加式日志中判断哪段已经过时。

### 6.2 各类事实由哪里维护

| 事实 | 规范来源 | 使用它的页面 | 防漂移方式 |
| --- | --- | --- | --- |
| 用户接受标准 | 用户旅程与 `testing/acceptance.md` | 教程、测试、证据页 | 旅程到页面 / 检查的追踪表 |
| API 字段与权限 | 实际路由和 contracts | R01、SDK、指南片段 | schema / 路由覆盖审计，补齐后生成参考 |
| SDK 方法与类型 | 两套 SDK 公共导出 | R02 / R03、教程 | 源码抽取、类型 / 运行验证 |
| 默认值与限制 | 配置定义和实现常量 | R04 / R07 | 尽量提取，无法提取的值有来源和审阅者 |
| 能力声明 | 注册表与 adapter capabilities | I02 / I14 / I18 | 自动表格加人工解释；不混入测试状态 |
| 已验证范围 | 结构化验收记录与证据 | I22、页面验证信息 | 按版本和时间派生，不手写“全支持” |
| 部署与凭据边界 | 架构契约和实际实现 | C02 / C06、运维 | 相关实现变更必须触发内容审阅 |
| 用户看到的 UI 文案 | en / zh-CN catalogs | 教程截图、操作指引 | 双语言复核，引用实际名称 |

架构设计、实现和验收结果发生冲突时，先标为待核实，记录冲突并定位当前版本；不能仅凭“代码如此”缩小承诺，也不能仅凭计划文件把未交付能力写成现状。

### 6.3 示例工程设计

建议建立一套共享、可重复运行的小型项目任务，并在其上维护分层示例；具体目录名在实施时决定，本方案不预设已有这些文件。

| 示例 | 支持文章 | 必须证明 |
| --- | --- | --- |
| 最小 Session | S04、S05、E01 | 双 SDK、真实 Run、小产物、查询、清理 |
| 项目修改 | S06、B02、B03、B08、B09 | 上传、修改、固定测试、预览、第二轮、产物留存 |
| 应用后端 | B01、B04、B11 | 业务标识映射、幂等保存、流恢复、重启恢复 |
| 工具授权与审批 | B05、B06、B07、I19— I21 | 等待、恢复、拒绝、一次写入、取消竞态 |
| 空闲与唤醒 | B10、C08、Provider 页 | 分组合证明文件 / 对话连续性、资源映射和清理 |
| 不确定结果恢复 | O07、B11、D06 | 不盲重试、准确对账、保留未决资源信息 |

片段从这些完整示例中提取，避免页面内各自维护一份逻辑。所有示例能够输出必要标识以便恢复；公共示例输出脱敏，真实 resource IDs 保存在用户的私有本地记录。

### 6.4 API、SDK 和 Agent 阅读体验

- 先审计公共路由，再决定 OpenAPI 的生成 / 校验方案；不可先发布一份与实现不同的手写规范并称其为权威。
- Python 与 TypeScript 的示例切换保留同一业务任务和版本；URL 或页面偏好记忆语言选择，但不能藏掉差异说明。
- 页面可提供干净 Markdown 导出，供搜索和编程 Agent 阅读；如建设 `llms.txt`，其作用是索引已发布规范页面，不是重复维护全站正文。
- 错误信息、状态和 capability 名称使用精确 API 标识，帮助全文搜索。自然语言描述提供常用中文 / 英文别名。
- “Ask AI”只能在规范内容可追溯、版本明确后考虑；搜索或问答结果不能代替接口参考和证据页。

## 9. 质量门禁与维护机制

### 9.1 一篇文章可以发布的条件

1. **有明确问题**：标题与摘要说清用户要做什么，不与另一篇文章承担同一规范责任。
2. **有真实来源**：关键字段、默认值和行为对应源码 / 契约；外部事实有官方链接与核查日期。
3. **示例可执行**：依赖、版本、鉴权、输入、输出和清理齐全；伪代码明确标注。
4. **成功可判断**：说明要观察的结果，不以“没有报错”代替完成标准。
5. **失败有出口**：至少覆盖该任务最重要的失败 / 未知结果，不导致重复资源或外部写入。
6. **验证不越界**：实云、模拟、契约测试、计划分开；双 SDK 完整旅程分别验证。
7. **边界不丢失**：租户、凭据、事件持久化、取消、未知结果与清理原则符合工程约束。
8. **语言和导航完整**：链接有效，术语一致，版本明确，有下一步；截图不泄露敏感数据。

### 9.2 建议建设的检查流水线

| 检查 | 自动化部分 | 人工判断 | 运行范围 |
| --- | --- | --- | --- |
| 内容结构 | frontmatter、ID 唯一性、内部链接、重复路径 | 标题是否真正解决用户问题 | 文档变更 |
| 参考一致性 | 路由 / schema / SDK 导出覆盖、参数示例校验 | 权限与副作用解释是否完整 | 契约变更 |
| 代码示例 | 抽取、类型检查、可安全执行的本地检查 | 依赖和预期结果是否充分 | 示例或 SDK 变更 |
| 确定性行为 | fixture / simulation / contract tests | 不能代替哪些真实能力 | 对应模块变更 |
| 真实旅程 | 显式配置账户后的验收脚本 | 失败归因、未决资源、真实清理 | 明确安排的实云验收，不在普通文档 PR 中隐式运行 |
| 兼容性摘要 | 读取结构化结果，检查证据链接 | 是否能外推到当前版本 | 证据 / 注册表变更 |
| 翻译和 UI | catalog / 术语 / 内容版本差异 | 中英文可读性、截图、交互步骤 | 文案 / UI 变更 |

这些是待实施门禁，不代表本次已经运行产品测试或建设流水线。实际命令以当时 `package.json` 和仓库实现为准，结果写入真实证据；不得创造“通过”的命令记录。

### 9.3 内容负责人和变更触发规则

- 每个栏目指定内容维护责任人；每个公共契约指定工程审阅者。当前未指定姓名，不能写成已有组织分工。
- Session / Run / 事件变更触发 S04、B01 / B03 / B04 / B11、C01 / C04、R01—R06 审阅。
- Provider 或 Harness 变更触发对应集成页、I01 / I02 / I14 / I22、C07 和 D03 / D04。
- 授权 / 审批 / 凭据变更触发 B05—B07、C06、O04 / O05、I19—I21 和参考权限说明。

### 9.4 语言与版本策略

开源文档目标为英文与简体中文等价覆盖。首批应至少同步完整上手闭环、关键安全 / 恢复边界和核心参考；其他未同步页面明确语言回退与版本，不挂空白译文。选择哪一语言为原稿属于编辑流程，不影响两种语言最终承诺一致。

参考按发布版本维护，教程明确 SDK / 控制平面版本。Provider 外部条件变化通过兼容性页补充核查日期。搜索结果显示版本和语言；旧版内容可以保留，但必须有明显版本提示。若产品尚无稳定版本体系，先使用可追溯 revision，并在发布流程建立后迁移，不能给未发布版本造名称。

### 9.5 衡量文档是否有效

优先观察：从 README 到首个成功 Run 的路径、安装与云执行各自耗时、双 SDK 首次成功率、首个产物获得率、清理完成率、故障页找到有效动作的比例、真实支持问题中由文档缺失造成的重复问题。

没有埋点时，可以通过自愿参与的走查和带明确范围的验收记录测量。不要为了文档指标引入默认收集用户任务文本、凭据、私有资源 ID 的遥测。阅读量和页面数量只作辅助，不作为内容架构成功的主要证据。
