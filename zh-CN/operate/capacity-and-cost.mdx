---
title: "管理容量、配额与成本"
---

Hexagon 的使用涉及控制平面和数据库、Sandbox 计算与存储、模型请求，以及可能收费的外部 Tools。分别记录这些资源，不能从“Run 已完成”或“Session 已休眠”推断全部计费已停止。

## 从工作负载估算

先记录每天任务数、平均活动时长、峰值并发、每 Session 轮数、平均产物大小和保留时长。以下是容量测量方法，不是供应商价格报价：

- 稳态活动 Session 数可用到达速率乘平均活动时长估算；突发和长尾需单独预留。
- 每日新增产物量约为完成 Run 数乘平均导出 bytes；数据库还有事件、输入、历史和索引开销。
- 模型与工具调用由实际请求量和供应商计量决定；重试、授权验证和集成检查也可能产生使用量。
- 计算停止后可能继续保留磁盘、快照或关联端点，必须检查相应 Provider 状态。

例如每小时 60 个任务、平均活动 120 秒，平稳流量的平均活动量约为 2；这不能证明两台资源足够，因为任务可能同时到达，且云启动和模型延迟有长尾。用真实峰值和实测排队时间校正。

## 一个可复算的工作负载样例

以下是假设数据，不是性能测量或费用报价：每天接收任务 8 小时，均匀到达率 60 Run/小时，每个 Run 平均执行 120 秒，每个 Run 捕获 4 MiB 产物，保留 30 天。先假定没有失败重试、授权等待、启动、空闲和清理开销；实际规划必须补回这些开销。

| 量 | 计算 | 结果与用途 |
| --- | --- | --- |
| 每日 Run | 60 × 8 | 480，作为每日工作量 |
| 平均同时执行需求 | 60 × 120 / 3600 | 2，表示平稳流量的服务需求，不是部署已达到的能力 |
| 每日有效执行时间总和 | 480 × 120 / 3600 | 16 资源小时，不等于供应商计费小时 |
| 每日产物净增长 | 480 × 4 MiB | 1920 MiB，即 1.875 GiB |
| 30 天产物字节 | 1.875 × 30 GiB | 56.25 GiB，尚未计入数据库索引、事件、输入、备份与副本 |

若同时到达十个任务，平均值 2 不能代表峰值容量。若新增的审批等待使资源保留时间延长，纯执行时间也不能代表资源占用。记录到达量、排队时间、启动时间、执行时间和关闭确认时间的分布，尤其是长尾，再决定入口限流与容量。

## 补回开销，避免重复计数

做一次敏感性估算：假定每天每个 Run 分配独立资源，启动耗时 30 秒，执行结束后资源继续保留 60 秒，10% 的 Run 在同一资源上额外执行一次 120 秒的尝试。同一资源内这些时间段互不重叠：

| 新增项目 | 假设的每日资源占用 |
| --- | --- |
| 启动 | 480 × 30 / 3600 = 4 小时 |
| 执行后保留 | 480 × 60 / 3600 = 8 小时 |
| 额外尝试 | 48 × 120 / 3600 = 1.6 小时 |
| 加上基准执行的 16 小时 | 29.6 资源小时 |

这是特定资源生命周期假设下的占用量，不是账单，也不是建议遇到失败就重试。结果未知的尝试必须先对账，再决定是否能安全重试；若重试重新分配资源，还需增加其启动与保留开销。跨 Run 复用资源会改变算法：对每个资源取已分配时间区间的并集，再跨资源求和，不要把同一段热资源保留时间计入每个 Run。供应商实际计量与取整规则另行应用。保留存储、模型请求、Tools 和控制平面仍需单独记录用量。

## 默认 worker 的容量边界

当前默认启动入口构造一个 `ExecutionWorker`；其循环领取一个 Run 后等待该次 `execute` 返回，再领取下一个。数据库 lease / fencing 解决接管和过期写入，不自动证明某个多进程部署具有经过验收的横向扩展能力。

在上述理想样例中，单个串行执行槽每小时最多处理约 30 个 120 秒任务，且尚未计入其他开销；60 个/小时的持续输入会积累等待。这是按假设推算的下限风险，不是基准测试。不要仅增加 Session 数量就宣称解决吞吐，也不要把“每 Session 一个活动 Run”和“整个部署能同时执行多少 Run”混为一谈。多 worker 部署需要另行验证共享配置、数据库、凭据入口、资源锁和故障接管。

## 观测与处理顺序

| 观察到的情况 | 先查什么 | 安全动作与完成信号 |
| --- | --- | --- |
| queued 持续增长 | 输入速率、worker busy / 就绪、Run 等待时长 | 在应用入口限流并排查执行能力；以等待时间下降且任务正常完成判断改善 |
| `sandbox_quota_exceeded` | 对应创建操作是否明确 `rejected`、Provider 账户配额 | 先解决额度或并发压力；该失败不自动把原 Run 重新排队 |
| `sandbox_creation_unconfirmed` / unknown | 原操作 ID、已记录资源 ID、Provider 实际结果 | 对账原操作；未确认前不通过新建 Session 盲目补发创建 |
| 模型或 Tool 限流 | 实际上游错误与请求量，和云分配配额分开 | 按已确认的失败边界安排应用策略，不能认为增加 Sandbox 就会提高上游额度 |
| closing 长期不结束 | 删除操作、快照 / 关联端点及 unknown 状态 | 核对 Provider 特定的删除完成证据及关联资源；保持私有资源标识供追查 |
| 数据库增长快 | Artifact 字节、事件、输入、索引和备份 | 按经验证的保留方案归档；不能将下载副本误当作原记录已经删除 |

`/v1/overview` 的 active_runs 统计非终态 Run；`/v1/sessions/activity` 衡量任务活动，分类可能重叠。这些都不是 CPU 或账单指标。Fleet 是持久状态快照且只返回最近至多 200 个 Session，不能用它证明账户全局资源已清空。结合完整分页记录和 Provider 侧检查，见[监控契约](/zh-CN/reference/monitoring)。

本页不列动态单价。制作预算时，在自己的预算记录中填写所选 Provider / 模型官方价格页、查询日期、账户套餐、区域、计费单位及相关存储或网络项，再乘以实际测量的使用量。不同单位不能直接相加，测试失败与清理等待也不能从用量中删掉。

## 并发与账户限制

单 Session 只有一个活动 Run。应用队列、worker 调度与 Provider 同时分配配额是不同限制。将任务拆成多个 Session 不会增加供应商账户配额，也不能绕过原任务需要的共享工作区。

Provider 支持的规格和试用限制会变化；按你的账户当前官方控制台核对。本页不复制动态价格或将历史测试账户额度作为永久规则。查看实际 allocation 错误和配额，再决定排队或降低并发。

## 空闲与到期

idle_timeout 控制可用策略的空闲资格，不是统一计费开关。Provider managed standby 时序独立；睡眠可能产生存储费用。控制平面停机期间无法保证执行平台负责的删除期限。

关闭不用的 Session 并确认关联资源清理。定期检查 unknown 和 closing，不用“本机进程已停止”当作费用结束证明。为长时间等待审批的任务制定业务处理方式，它们仍是活动 Run。

## 应用控制措施

限制入口并发、为任务保存可恢复标识、监控运行时长与等待原因、主动归档需要保留的产物、关闭完成的工作区。重试保留幂等键，未知创建结果对账，避免意外重复资源。

对每个候选组合做小规模真实测量：启动时间、有效执行时间、产物量、恢复时间和清理确认时间。把失败尝试也计入使用分析。优化前后保持同一任务和成功标准，不以减少验收步骤获得好看的结果。
